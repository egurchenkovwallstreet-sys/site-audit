# ТЗ: масштабирование под рекламу и ≥20 параллельных сканов

**Проект:** site-audit (152-ФЗ, 168-ФЗ, SEO, security).  
**Статус:** **не начато** — фаза A (качество одного скана) в приоритете; этот документ — целевая картина **перед/во время** рекламных кампаний.  
**Связь:** сейчас сканы выполняются в `BackgroundTasks` одного процесса uvicorn (`backend/app/api/scans.py`, `scan_runner.py`).

---

## 1. Цель

1. Выдерживать **массовый вход** с рекламы (десятки–сотни `POST /api/scans` в час).
2. Обеспечить **не менее 20 одновременно выполняемых полных сканов** в пике (или эквивалент: 20 слотов воркеров с честной очередью для остальных).
3. Сохранить честный scope, антибот-политику и фазу A (все findings на экране без обрезки по тарифу) — см. `docs/report-policy.md`.

**Не цель:** гарантировать 20× ускорение **одного** скана; ускорение одного прогона — отдельный подпункт (§6).

---

## 2. Исходная точка (as-is, замеры 2025-11)

| Параметр | Значение |
|----------|----------|
| Прод VPS | ~2 vCPU, ~3.8 GiB RAM |
| Процесс | 1× uvicorn, 1× Chromium (Playwright), Nuclei в том же контейнере |
| Очередь | Нет; каждый запрос → `BackgroundTasks` |
| Бюджет скана | до 600 с, до 22 страниц, Playwright до 14 URL |
| 1 скан Darom (регрессия) | ~40 с в одиночку |
| 2 скана параллельно (example + Darom) | ~149–162 с каждый (конкуренция за CPU/браузер) |

**Вывод:** текущий прод — **MVP для ограниченной нагрузки** (единицы–десятки сканов в день, **1–2** параллельных полных скана комфортно). Запуск рекламы без §4–§8 — риск деградации, таймаутов, OOM.

---

## 3. Целевая архитектура

```
Клиент (web / mobile)
    → API (FastAPI, только приём и статус)
    → Redis (очередь scan_jobs)
    → Worker pool (N процессов/контейнеров scan-worker)
        → fetch_scan_site, compliance, SEO, security, Nuclei
    → PostgreSQL (scans, findings)
```

| Компонент | Ответственность |
|-----------|-----------------|
| **API** | Валидация URL, создание `Scan` (`pending` / `queued`), rate limit, `GET` статус/findings |
| **Redis** | Очередь задач, опционально pub/sub для прогресса |
| **Scan-worker** | Исполнение `run_compliance_scan`; **свой** event loop, **свой** Playwright (или пул браузеров на воркер) |
| **Postgres** | Единый источник истины; пул соединений под N воркеров |

**Запрещено для масштаба:** N uvicorn workers в одном контейнере с общей памятью (N× Chromium без изоляции).

**Референс в репозитории:** `docs/architecture.md`, `docker-compose.yml`.

---

## 4. Продуктовые требования (UX)

1. Статусы скана: `queued` → `running` → `completed` | `failed`.
2. В UI `/check/{id}`: **позиция в очереди**, ориентир времени ожидания до `running`.
3. После старта — существующий прогресс (таймер, шаги).
4. При переполнении очереди (порог настраиваемый, напр. >50 `queued`): сообщение «Высокая нагрузка, попробуйте через N минут»; опционально 503 на `POST /api/scans`.
5. **Rate limit** без авторизации: например 3–5 сканов / час / IP (точные цифры — при внедрении).
6. Повтор того же URL за 24 ч: режим **кэша** (отдельная задача: показывать «свежий отчёт от …» + кнопка «обновить»).

**Тарифы:** массовый бесплатный **экспресс** (меньше страниц, без Nuclei) vs **полный** скан — согласовать с `docs/report-policy.md` и фазой B (оплата).

## 5. Железо и ёмкость «20 параллельных»

### 5.1. Полный скан (как сейчас)

Ориентир на **20 одновременных** тяжёлых прогонов:

- **20–40 vCPU** суммарно у воркеров, или **4–8 воркеров × 4–8 vCPU**
- **16–32 GiB RAM** на пул воркеров (≈300–800 MiB на активный Playwright)
- Быстрый диск, достаточный **исходящий** канал
- Выделенные **Postgres** и **Redis** (не на том же 2 vCPU, что 20 браузеров)

### 5.2. Прагматичный компромисс под рекламу

| Режим | Параллельность | Назначение |
|-------|----------------|------------|
| **Экспресс** | до 20+ | Лендинг с рекламы, 5 страниц, без Nuclei, ~1–2 мин |
| **Полный** | 5–10 в пике, остальное в очереди | Глубина 152-ФЗ + Nuclei |

Конфиг через `.env`: `SCAN_MAX_PAGES`, `NUCLEI_ENABLED`, `SCAN_TIME_BUDGET_SEC`, `MAX_CONCURRENT_SCANS`.

### 5.3. Параметры воркеров (целевые)

| Переменная | Назначение | Старт |
|------------|------------|-------|
| `MAX_CONCURRENT_SCANS` | Слотов выполнения в пуле | 4 → 20 |
| `WORKER_COUNT` | Число процессов/контейнеров | 2 → 10 |
| `QUEUE_BACKEND` | `redis` | обязательно на проде масштаба |

## 6. Ускорение **одного** скана (без ломки scope)

Параллельно с очередью, внутри `fetch_scan_site` / `scan_runner`:

| Улучшение | Ожидаемый эффект | Риск |
|-----------|------------------|------|
| `asyncio.gather` загрузки страниц + `Semaphore(4–6)` | −30–50% на тяжёлых сайтах | 429, антибот |
| После обхода: параллельно SEO + technical + 168-ФЗ | −10–20 с | низкий |
| Кэш SPA-бандла (`main.dart.js`) в рамках одного scan_id | быстрее Flutter-сайты | RAM |
| Nuclei только при остатке бюджета | уже частично есть | — |

Не увеличивать агрессию к целевым сайтам (роботы, частые запросы) без лимитов per-host.

## 7. Надёжность и эксплуатация

1. **Мониторинг:** длина очереди, активные воркеры, % `failed`, p95 длительности скана, CPU/RAM воркеров.
2. **Алерты:** очередь > N, error rate > X%, воркер не heartbeat > 5 мин.
3. **Регрессия:** `scripts/vps-regression.sh`, cron — сохранить; добавить **нагрузочный** сценарий (см. §9).
4. **Деплой:** API и workers отдельно; без перезаписи `.env` на сервере — `docs/deploy-workflow.md`.
5. **Логи:** `scan_id`, длительность фаз, `pages_checked` — для разбора инцидентов после рекламы.

---

## 8. Юридика и злоупотребления

1. Явное согласие в UI: сканировать **только свои** сайты (или с разрешением).
2. Блоклист IP/ASN при злоупотреблении.
3. Пассивный режим сохранять: не эксплуатировать уязвимости.
4. Отчёты и штрафы — ориентиры, не юрзаключение (уже в политике отчётов).

---

## 9. Экономика и монетизация

1. Оценить **себестоимость** одного полного скана (CPU-секунды × цена VPS).
2. До массовой рекламы: решить, что бесплатно (экспресс), что за оплату (полный PDF/лимиты) — `docs/report-policy.md`.
3. Иначе реклама → тысячи бесплатных 10-минутных сканов без выручки.

## 10. Этапы внедрения (дорожная карта)

| Этап | Содержание | Критерий готовности |
|------|------------|---------------------|
| **M0** | Документ согласован, метрики as-is зафиксированы | этот файл + замеры в §2 |
| **M1** | Redis + arq/Celery; статус `queued`; 2–4 воркера; `MAX_CONCURRENT_SCANS=4` | 50 POST подряд без падения API; очередь видна в UI |
| **M2** | Параллельный fetch страниц; rate limit IP; кэш домена 24 ч | p95 полного скана −20% на эталонах |
| **M3** | Масштаб воркеров до 20 слотов; отдельные хосты PG/Redis | нагрузочный тест §11 — pass |
| **M4** | Автоскейл по длине очереди (опционально K8s) | пик рекламы без ручного тюнинга |

**Не запускать массовую рекламу** до прохождения **M1** (очередь + честный UX) и **M3** (или осознанный режим «экспресс only» на M1).

## 11. Нагрузочный тест (acceptance)

Скрипт в репозитории: `scripts/bench_parallel_scans.sh` (на VPS, LF line endings).

**Сценарий приёмки M3:**

1. Подготовить 30 URL (mix: лёгкие + 5 тяжёлых из `regression_urls.json`).
2. Отправить **30 POST** за **≤2 мин**.
3. Ожидание: все `completed` или `failed` с причиной; **не** зависшие `running` > 2× бюджета.
4. **≥20** сканов одновременно в `running` не менее **60 с** (при целевом железе).
5. API latency `GET /api/scans/{id}` < 500 ms p95 во время теста.
